# EtherCrab Windows x64 source review

The implementation pins EtherCrab 0.7.1 source at `fec2730823ce1eb62425f83d5df49d678f03b104`. The Windows std backend owns a blocking Npcap capture, requests immediate and nonblocking receive, queues raw Ethernet TX, and passes EtherType 0x88A4 replies to EtherCrab PDU storage. The Windows example uses an Npcap interface identifier such as `\Device\NPF_{GUID}` and recommends the x64 Npcap SDK import libraries for compilation. Ethernet capture and injection use the installed Npcap NDIS filter. An admin-only installation restricts driver access and may require elevation. The Workbench uses Npcap directly for its dedicated cycle thread. It delay-loads the installed DLL from the system Npcap directory, so offline commands and GUI startup can run without the driver. [EtherCrab Windows backend](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/src/std/windows.rs), [Windows setup](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/doc/ek1100-windows.md), [Npcap user guide](https://npcap.com/guide/npcap-users-guide.html)

EtherCrab's manifest and README offer MIT or Apache-2.0. The pinned source checkout lacks the root license files linked in the README. The portable build selects Apache-2.0 for EtherCrab, includes that license in the dependency notices, and records the exact upstream source. Npcap's free edition has a limited deployment allowance and does not grant redistribution. OEM redistribution is a separate license. The package ships the Workbench binaries and notices. Install Npcap from its publisher under the applicable terms. [EtherCrab licensing declaration](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/README.md#license), [Apache License 2.0](https://www.apache.org/licenses/LICENSE-2.0), [Npcap downloads and license terms](https://npcap.com/#download), [Npcap OEM redistribution](https://npcap.com/oem/redist)

EtherCrab's initialization performs broadcast reset and writes station, EEPROM access, SyncManager, FMMU and DC registers. It reads SII identity and builds the process image from live SII/CoE configuration. `into_pre_op_pdi` configures input FMMUs first from logical address zero for the first group. The Workbench requires a separate approval for these setup writes and SAFEOP/INIT state transitions. It checks the bus count before starting EtherCrab, checks exact identity before configuring FMMUs, and compares actual Tx/Rx lengths with the profile. Read-only discovery uses broadcast and auto-increment register reads to show count, bus order, links, alias and AL status. SII identity appears after approved setup because its read protocol writes ESC request registers. [MainDevice initialization](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/src/maindevice.rs), [Group PDI configuration](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/src/subdevice_group/mod.rs)

The stock cyclic `tx_rx` sends LRW (Logical Read Write) with the group image and returns its aggregated Working Counter and state. The pinned public command API lacks LRD. The Workbench emits one read-only LRD for the input range plus an FPRD for AL state and status code in the same frame. It expects LRD WKC 1 and AL WKC 1 for the single device. A valid exchange also requires SAFEOP and no AL error. This covers an input-only bench run with RxPDOs present while keeping staged bytes on disk and in memory. SAFEOP is expected to update inputs on devices that support this mode. Physical bench acceptance is device-specific. [EtherCrab commands](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/src/command/mod.rs), [Beckhoff EtherCAT commands](https://infosys.beckhoff.com/content/1033/tc3_io_intro/1257993099.html), [Beckhoff EtherCAT state machine](https://infosys.beckhoff.com/content/1033/el2535/1036980875.html)

The stock Windows example uses a relative cycle wait with spin sleep after subtracting elapsed work. The Workbench compares the same relative policy with a monotonic absolute deadline schedule that skips expired slots. Both use the same cycle and logging code and the same spin sleeper. The request, observed host-side send/receive gaps, and configured/reported device synchronization are separate values. Native Windows scheduling and the NIC/driver can introduce jitter. The 1 ms period is a bench measurement target. [EtherCrab Windows example](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/examples/ek1100-windows.rs), [EtherCrab Windows tuning notes](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/doc/windows-tuning.md)

The single-device LRW gap is handled by the LRD path. Compare SOEM on the same bench if the selected device cannot enter SAFEOP or return valid input through this path. In that comparison, isolate PDO assignment, SM/FMMU layout, DC mode, driver and scheduler variables. No bench model was selected during the initial build.

The November 12 update reads the ESC SyncManager count and enabled process-channel registers after FMMU setup. It uses those channels to read CoE assignment objects and mapping descriptors, with a ten-second budget for starting readback requests and cancellation checks. An active request remains subject to EtherCrab's command timeout. This follows the pinned source's per-SyncManager byte alignment and avoids querying CoE 0x1C00, which upstream documents as timing out on some devices. A complete direction is compared with the profile. Partial readback is reported as unavailable, and a confirmed field-order or length conflict stops before SAFEOP. The helper compiles against EtherCrab. Physical SDO and register readback acceptance remains pending. [Pinned PDO configuration source](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/src/subdevice/configuration.rs)

The virtual ESC fixture exercises EtherCrab initialization through the same packet interface as the Npcap route. Its SII and CoE responses are authored for a fixed one-device profile. The fixture validates process SM/FMMU configuration and can inject setup and cleanup faults. A SAFEOP-with-error response exposed that the pinned group state wait compares the state value without rejecting its AL error flag. Workbench adds a separate AL status/code confirmation and preserves failure diagnostics before requesting INIT with acknowledgement. [Pinned group state wait](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/src/subdevice_group/mod.rs), [Pinned AL reset encoding](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/src/al_control.rs)

The DC diagnostic update distinguishes startup register programming from clock synchronization. Pinned initialization resets DC system time, offset, propagation delay, activation and cycle registers, latches port receive times, and writes initial offsets and propagation delays on DC-capable devices. The offset and delay writes ignore WKC upstream, so the report calls this an attempt and retains their separate readbacks. Workbench configures zero static-sync iterations and its LRD-only cycle sends no FRMW. It never calls `configure_dc_sync`. Enhanced-DC activation is read back after SAFEOP; active cyclic/SYNC bits or unavailable activation stop before input cycling and trigger INIT cleanup. The in-memory CoE/DC model exercises the capability and initial-offset path. It is not a model of oscillator drift, SYNC pulse generation or physical synchronization accuracy. [Pinned DC initialization](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/src/dc.rs), [Pinned register reset](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/src/maindevice.rs), [Pinned DC group configuration and cyclic FRMW](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/src/subdevice_group/mod.rs)

## CoE upload coverage in version 0.9.0

The pinned generic reader rejects the legal zero command specifier in an upload-segment response: its shared `CoeCommand` enum has no zero variant. A Rust integration test reproduces the decode error using an authored segmented response, then reads the exact marker and device name through the Workbench uploader. Source inspection also finds a shared twelve-byte trim despite the nine-byte segmented header, discarded initial partial data in the segmented branch, and no response toggle/counter comparison. The decode failure occurs first in this fixture; the later issues are source findings. [Pinned CoE reader](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/src/mailbox/coe/mod.rs), [command and segmented headers](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/src/mailbox/coe/headers.rs), [service layouts](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/src/mailbox/coe/services.rs)

Workbench now serializes its own read-only uploads after PDI setup. It discovers enabled mailbox SyncManagers, requires disjoint 16–1,024 byte mailbox ranges outside ESC registers and process images, and confirms that the layout did not change during setup. It continues the 1–7 counter sequence observed in successfully injected EtherCrab mailbox requests. Response checks cover mailbox length/type/counter, CoE service, initiation/abort identity, command, toggle, exact primitive size, declared total, final segment and padding. Segment payload starts at byte nine; partial initial data is retained. A protocol, size or timeout failure latches the uploader unhealthy and stops before SAFEOP. A valid server abort can leave an optional field or mapping unavailable. Unexpected pending responses and emergency messages fail setup; automatic mailbox repeat/recovery is not implemented.

Each object is bounded to 4,096 bytes and 128 segments, with a 500 ms elapsed budget checked between commands and polls. An in-flight PDU remains subject to its separate timeout, so this is not a hard wall-clock deadline. The optional UTF-8 device name has a 128-byte bound; PDO primitives require exact sizes. Normal/segmented replies without a declared total, complete access and SDO downloads are unsupported. Cancellation releases the PDU future and proceeds with the existing INIT confirmation. These setup allocations and mailbox polls run outside cyclic I/O and CSV writing.

The original `into_pre_op_pdi` still uses EtherCrab's private expedited-only helper to obtain small PDO objects. Workbench has not replaced that initializer. The new normal/segmented models deliberately switch policy only after the authored SM/FMMU image is configured. They establish post-setup readback coverage, not acceptance of devices requiring other upload forms during initialization. [Pinned PDO initializer](https://github.com/ethercrab-rs/ethercrab/blob/fec2730823ce1eb62425f83d5df49d678f03b104/src/subdevice/configuration.rs)

SOEM's `ecx_SDOread` accepts normal and segmented replies, retains the initial data and copies segment data after the nine-byte header. This makes it a comparison candidate if a selected device exposes the remaining initializer limitation. No SOEM backend was integrated, built or benchmarked. Its current source declares GPLv3/commercial dual licensing, so substitution would require a separate licensing and packaging review. Device-specific need remains unknown. [SOEM CoE source](https://github.com/OpenEtherCATsociety/SOEM/blob/master/src/ec_coe.c), [SOEM license](https://github.com/OpenEtherCATsociety/SOEM/blob/master/LICENSE.md)
