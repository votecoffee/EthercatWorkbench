# Offline Ethernet capture inspection

Saved **classic Ethernet PCAP 2.4** and an **Ethernet PCAPNG subset** can be inspected through the CLI and desktop saved-file review panel. Version 0.23 adds explicit selection from up to 32 PCAPNG interfaces within one section. The inspector detects the container from its bytes, reads a bounded file using Rust file I/O, and never loads Npcap, opens a NIC or transmits packets. The desktop runs the same inspector on its cancellable file worker and retains a frozen copy of the current commissioning profile. See [desktop instructions](desktop-review.md#inspect-ethernet-pcap) for inputs, quality/timing views and export.

```powershell
.\ethercat-workbench-cli.exe inspect-pcap .local/bench.json .local/bench.pcap --station 0x1000 --preview 16 --out .local/inspection.json
.\ethercat-workbench-cli.exe inspect-pcap .local/bench.json .local/bench.pcapng --station 0x1000 --out .local/inspection-ng.json
.\ethercat-workbench-cli.exe inspect-pcap .local/bench.json .local/multiple-nics.pcapng --interface 1 --out .local/interface-1.json
```

Use the effective profile saved with the corresponding run. `--station` accepts decimal or `0x` hexadecimal and defaults to `0x1000`, EtherCrab's initial configured station address in the current one-device path. Supply the actual configured address when it differs. The address, profile identity, image length and field definitions are expectations supplied by the operator. This inspection does not discover or confirm device identity, mapping or field meaning.

`--interface ID` accepts decimal IDs 0–31 for PCAPNG only. Omit it for a sole interface. A file with multiple descriptors requires an explicit choice even when only one interface has packets or uses Ethernet; an ambiguity error lists IDs, link types and packet counts. The selected interface must be Ethernet. Counts, previews, first/last timestamps, regressions and spacing use only its packets. Preview packet indexes remain one-based positions among **all** Enhanced Packet Blocks in file order, so gaps can represent excluded interfaces. No timestamps or spacing are pooled across interfaces. An empty selected interface produces zero selected counts and unavailable first/last timestamps.

The CLI writes JSON to stdout. Optional `--out` writes UTF-8 without a BOM and with a final newline, flushes it before stdout, and requires a new `.json` path. Existing files are preserved. Parse errors return a nonzero exit code and produce no inspection export. A structurally readable capture with no matching frames or invalid input quality still produces a report and exits successfully; inspect its counts and notes.

## Recognized frames and input quality

The inspector uses the same reply parser as the live input-only path. It recognizes untagged EtherType `0x88A4` frames with the Workbench MAC signature, one LRD at logical address zero of exactly the profile's TxPDO length, followed by one six-byte FPRD of AL status at the selected station's `0x0130`. Exact outbound Workbench frames are counted separately. Other EtherCAT traffic remains unmatched. This is a deliberately limited Workbench trace inspector, not a generic EtherCAT protocol analyzer.

For each recognized returned frame, input WKC must equal one, the AL-register WKC must equal one, the low five AL-status bits must equal SAFEOP with no error flag, and the AL code must equal zero to count as `valid_safeop_replies`. Input WKC and AL failures are counted independently and can overlap. A preview retains both WKCs, raw status and code, sequence, packet index, capture timestamp, raw payload and profile-decoded typed values. Invalid previews remain explicitly labeled; decoded bytes alone are not valid input evidence. All TxPDO fields are decoded, including fields excluded from logging, with the same bit, endian and word transformations as the offline payload decoder.

Requests and returned frames are counted independently. The inspector does not correlate pairs, discard duplicates, infer timeouts or create application cycle indexes, generations or missed-deadline counts. A reply can appear without its request in the saved file. Sequence reuse or a stale frame therefore does not establish a fresh exchange. This differs from live reply matching against one outstanding request and from the authored replay fixture's ordered candidates.

## Recorded timestamps and provenance

Reports retain raw-file SHA-256, byte count, full effective profile and its canonical JSON hash, application version, requested station, timestamp precision and the first/last packet timestamps. The first timestamp is also formatted as UTC. A metadata change detected during file reading rejects the result. Hashes identify the bytes analyzed; they are not signed provenance or an attestation of a physical capture.

New inspection reports use **schema 3**. `capture_format` is `pcap` or `pcapng`; classic results set `pcapng` to null. PCAPNG metadata retains section minor version/declared length, selected `interface_id`, Ethernet link type, snapshot length, decimal timestamp exponent, signed offset and block/skipped-block/skipped-option counts. It adds `selection_explicit`, `total_packets`, `skipped_packets` and an `interfaces` inventory with each ID, link type, snaplen, timestamp exponent/offset and packet count. `counts.packets + pcapng.skipped_packets == pcapng.total_packets`; the inventory counts sum to that total. This excludes skipped metadata blocks. The desktop shows the selection and inventory. Earlier schema-1/2 inspection files are preserved; inspection exports are not run reports or CSV-audit inputs. Run-report and profile schemas are unchanged.

Request spacing, returned-frame spacing and valid-returned-frame spacing are separate summaries. Each gives count, p50, p95, p99 and the exact longest gap, in nanoseconds. Percentiles use a three-significant-digit histogram. Zero gaps, including duplicate timestamps, are retained. With fewer than two matching frames, the gap count is zero and values are null. If any packet timestamp goes backward, all spacing summaries are null and the report retains the regression count and payload previews.

Capture timestamps use the clock and placement of the capture tool. The file does not establish whether timestamps were taken at injection, dequeue or the wire, whether the capture includes both directions, or how many packets the capture tool dropped. Declared nanosecond precision is not a measurement of accuracy. These summaries remain separate from the application's monotonic receive timestamps, configured device synchronization/DC settings and requested scheduler period. An external capture setup still needs qualification before its timestamps can support a physical timing claim.

## PCAPNG subset

The parser follows the block and timing layouts in the [IETF PCAPNG draft 05](https://www.ietf.org/archive/id/draft-ietf-opsawg-pcapng-05.html), a work-in-progress specification. The supported subset is one Section Header Block, 1–32 Interface Description Blocks and timestamped Enhanced Packet Blocks. IDs start at zero in descriptor order; each packet must reference a prior descriptor. Both byte orders and section versions 1.0/1.2 are accepted. Declared section lengths and repeated block lengths must agree with the file. Block/option lengths, four-byte alignment, interface references, packet lengths and padding bounds are checked before slicing; packet padding is excluded from decoded bytes.

Interface timestamp resolution defaults to decimal microseconds. Explicit decimal microseconds (`if_tsresol=6`) or nanoseconds (`9`) are supported. Signed `if_tsoffset` seconds are applied using checked-range integer arithmetic with no rounding. Resulting Unix timestamps must be between zero and 9,223,372,036,854,775,807 ns. Other decimal/binary resolutions and out-of-range timestamps fail inspection. Offsets describe file timestamps; they do not establish clock accuracy or device synchronization.

Additional sections, untimestamped Simple Packet Blocks, obsolete Packet Blocks and duplicate/wrong-sized timing options are rejected. Non-Ethernet descriptors may be retained in the inventory and their packets excluded; they cannot be selected for decoding. Every interface and Enhanced Packet Block, including excluded ones, must satisfy the same supported timestamp, length, padding and option bounds. An unsupported clock or malformed excluded record fails the whole inspection. Declared nonzero FCS lengths and enhanced-packet FCS/offload/error/reserved flags are unsupported. Direction/reception flags are checked but do not determine which EtherCAT frames are requests or replies. Other well-bounded options and metadata blocks are counted as skipped. Their payloads, including interface names, comments and any capture-tool statistics, are not interpreted or exported. Skipped statistics do not establish zero capture loss. This is consumer validation of a subset, not complete PCAPNG conformance or generic protocol dissection.

## Bounds and unsupported input

- Maximum file size: 64 MiB; maximum packet count across all interfaces: 1,000,000; PCAPNG also has a 1,000,000-block limit, including metadata, and a 32-interface limit. The file is read into bounded memory before parsing. Each snapshot length must be 1–262,144 bytes. Every record length and timestamp fraction is checked before slicing.
- Both byte orders and microsecond/nanosecond timestamp variants of classic PCAP 2.4 are supported. The parser uses the public layout documented in [libpcap 1.10.5's savefile reader](https://github.com/the-tcpdump-group/libpcap/blob/libpcap-1.10.5/sf-pcap.c) and [file header definition](https://github.com/the-tcpdump-group/libpcap/blob/libpcap-1.10.5/pcap/pcap.h). It is an independent Rust implementation; no libpcap source is bundled or used for offline inspection.
- Modified/older PCAP formats, selected non-Ethernet link types and classic link-type words with additional FCS flags are rejected. VLAN-tagged traffic is counted as other traffic and is not unwrapped. No FCS validation is performed. Export a supported section/file when the source container uses unsupported features.
- A packet whose captured length is smaller than its declared original length is counted as snapshot-truncated and never decoded, even if its available bytes include the PDO. A physically truncated record or partial record header rejects the file.
- `--preview` is 0–64, default 16. All recognized frames contribute to counts and available spacing summaries; only the first requested number of returned frames retain payloads. Field names are bounded to 16 KiB combined for this report. There is no decoded CSV export or conversion into live/replay runs.

The desktop checks cancellation between 64 KiB file reads, packet records, PCAPNG blocks/options (including excluded interfaces) and 64 KiB raw-file hash chunks, and before publishing a result. A blocking file-system call, profile validation/serialization or one packet decode may delay cancellation. A cancelled job exports no partial result, and a success that finishes before cancellation is polled is discarded. The CLI retains its synchronous interface and emits the same schema-3 inspection result as the desktop.

The verification workflow generates all binary PCAP fixtures under ignored `.local/`. No vendor capture is committed. Coverage includes the desktop worker, frozen settings, cancellation, new-file exports and pure egui layouts with no native window or desktop input. Inspection of a selected physical device's capture and native GUI interaction remain pending.
